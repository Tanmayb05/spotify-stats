## What Was Implemented

### Purpose

Nothing in the pipeline asserted the warehouse was *correct* — `gold_star` checked
row counts (V1) and `refreshed_views` checked MV freshness (V7), and that was all.
Phase 13 adds a broad DQ suite as a pipeline gate, makes its results a product
surface, and reduces the app to the three pages the roadmap ends on.

### Features

- **21 checks** across all 6 required categories (uniqueness,
  referential_integrity, range, freshness, completeness, anomaly), registered via
  a `@check` decorator. `per_user_fact_freshness` fans out per user → 31 results
  on the 10-user dataset. 12 blocking, 9 warn.
- **`THRESHOLDS`** dict set below values measured on the real seeded DB with
  headroom, so the suite is green on first run.
- **`quality` schema** — a peer of bronze/silver/gold — with `dq_run` +
  `dq_result` and `public.dq_*` compat views.
- **Terminal Dagster asset `data_quality`** — owns `bronze.ingest_run.finish_run`
  (`success` / `partial`), raises on blocking (→ `run_failure_sensor` →
  `failed`), merges its summary into the `detail` JSONB.
- **`GET /api/health/data`** — DQ run + ingestion metrics + per-user freshness +
  quarantine + a 30-run trend, read entirely through `public.*` compat views so
  it works on both backends.
- **Data Health page** — pipeline status cards, ingestion funnel, match-rate
  chart, per-category DQ tabs, per-user freshness table, row-count trend,
  conditional quarantine section, informative empty states.
- **Insights page** — Overview + ListeningPatterns + Discovery merged; existing
  charts kept; `useTimeRange` hook extracted (slider re-clamp bug fixed).

### Implementation

`run.py` starts a `dq_run` row on its own short-lived transaction, opens one
read-only connection shared by all checks, catches a raising check into a
synthesised failed result (never aborting the suite), then writes `dq_result`
rows + the rollup on another own transaction. `summarize()` derives the run
status with `fail > warn > pass` precedence.

The `data_quality` asset calls `run_all`, logs every non-passing result, and — if
any blocking check failed — raises without calling `finish_run`. Otherwise it
reads the current `detail` (which `gold_star` populated with FK rates), merges the
`dq_*` keys, and calls `finish_run` with `partial`/`success`.

`/api/health/data` builds the backend through an `lru_cache` factory (lazy, since
`build_backend` raises without Supabase creds), then makes 7 `select()` calls each
wrapped in `try/except → []`, and assembles the response with per-category
rollups and the migration-011 invariants computed inline.

### Flow

```
nightly_ingest_job
  raw_streams → quarantine + silver_streams → gold_star → refreshed_views
    → data_quality  (run_all → persist quality.dq_* → finish_run | raise)

/api/health/data  ← reads public.dq_* + public.bronze_*  ← Data Health page
```

### Usage

```bash
docker compose up
docker compose exec dagster dagster job execute -j nightly_ingest_job -m dagster_project.definitions
docker compose exec api python -m app.quality.run          # ad-hoc, exit 0/1/2
curl localhost:3011/api/health/data
# web: localhost:3010/data-health
```

## Deviations from the roadmap

1. Migration is `013_dq_tables.sql`, not `012` — that number is taken.
2. `data_quality` is a terminal `@asset`, not a Dagster asset check (repo has
   zero `@asset_check`; an asset check can't own `finish_run`).
3. Roadmap's uniqueness checks on `dim_track` nat key + `fact_streams` PK are DB
   tautologies — replaced with `fact_ingest_id_unique` (no FK/unique) and
   `dim_track_uri_unique`.
4. `latest_ingest_run_terminal` is warn, not blocking, and ignores `running` rows
   — a stale `failed` predecessor must not fail today's already-rebuilt pipeline.
   Blocking set = 12.
5. `pandera_schemas.py` narrowed to bounded-sample contract validation; no shared
   code with `ingest/schemas.py` (different column set).
6. `enrichment_coverage` warn-only at threshold 0.0 (`audio_source='enriched'` is
   0% — audio-features enrichment doesn't exist in this repo).
7. `Insights.tsx` kept as one file, not 13 extracted components — the merged
   pages were self-contained, so it's a mechanical move.
8. `getListeningHeatmap` client fn dropped (zero callers); the route + RPC stay
   server-side.
9. API-baseline check done by eye (`compare_api_baseline.py` has no path filter):
   Phase 13 deletes endpoints and leaves survivor SQL untouched.
