## What Was Implemented

### Purpose

Give the app a real, queryable dimensional model instead of one wide table, so later
phases (12: incremental ingestion, 13: DQ gating, 14: feature store, 15: recommenders)
have dimension tables and a fact table to build on — while guaranteeing the existing
Insights/Recommendations pages kept showing exactly the same numbers throughout the
migration.

### Features

- **Medallion layers**: `bronze.raw_streams` (append-only landing, JSONB audit trail),
  `silver.streams` (typed, normalized keys), `gold.*` (5 dimensions + fact + 2 auxiliary
  tables).
- **Real dimension data**: 4,536 `dim_artist` rows (4,079 enriched from
  `artists_info.json`'s 4,216 records after case-insensitive key collisions, 457
  play-history-only stubs), 13,837 `dim_track` rows (808 enriched from the
  salvage-parsed `songs_info.json`, the rest stubs), 5,858 `track_lyrics` metadata rows
  (has_lyrics/source/word_count only, never text).
- **Genre backfill**: opt-in MusicBrainz enrichment script, raised genre
  coverage-of-plays from 53.1% pre-backfill to **78.2% post-backfill** (final,
  completed run — 682 of 1,886 candidate artists tagged, ~31 min at the documented 1
  req/s courtesy rate limit; cached at `outputs/enrichment/artist_tags.json`).
- **3 MVs + 8 RPCs repointed** at `gold.fact_streams`, byte-identical names/signatures.
- **`outputs/` dependency closed** (B5): `/api/reco` and `/api/simulate` now read
  `gold.dim_track`/`gold.dim_artist` when `DB_BACKEND=local`, falling back to the JSON
  files only if those tables are empty.

### Implementation

The riskiest part (migration 010's MV/RPC rewrite) required one design change beyond
the plan: the original `monthly_stats`/`top_artists`/`top_tracks` grouped by
**case-sensitive** artist/track name text
(`COUNT(DISTINCT master_metadata_album_artist_name)`), not the normalized
`dim_artist.artist_key`. This dataset has 4 rows that are case-only variants of the same
artist (`"KALEO"` vs `"Kaleo"`, `"LEN"` vs `"Len"`). Grouping by the normalized key would
have silently merged them and changed `get_top_artists`' counts. Fix: `gold.fact_streams`
carries denormalized, un-normalized `artist_name`/`track_name`/`album_name` columns
copied verbatim from `silver.streams`, and migration 010's rewritten MVs/RPCs group by
those — reproducing the old behavior bit-for-bit while still reading from `gold.*`. This
is documented as a design note in `DATA_MODEL.md` and inline in migration 009/010.

`build_star_schema.py` also had to add an explicit `refresh_all_views()` call at the end
of its run: the 3 MVs are created (and non-concurrently refreshed once) by migration 010,
but that happens *before* `fact_streams` is first populated by a `build_star_schema.py`
run, so a fresh `migrate.py` + `build_star_schema.py` sequence would otherwise leave the
MVs stale/empty until someone thought to refresh them by hand.

### Flow

`python db/migrate.py` (applies 008→010) → `python scripts/load_enrichment_to_db.py`
(populates dims from JSON) → optionally `python scripts/backfill_artist_tags.py`
(raises genre coverage) → `python scripts/build_star_schema.py` (builds
bronze→silver→gold, refreshes MVs). Each step is independently re-runnable.

### Usage

No API surface changed — every existing frontend page keeps working exactly as before.
The new capability is queryable: `SELECT * FROM gold.fact_streams JOIN gold.dim_artist
USING (artist_key)` now works for anything Phase 12+ needs, instead of parsing
`master_metadata_album_artist_name` text every time.

### What V4 caught (two real bugs, both fixed before the final clean run)

1. **Stale container copy.** The first `build_star_schema.py` run in the container was
   an out-of-date copy missing the `artist_name`/`track_name`/`album_name` columns added
   to `gold.fact_streams` partway through implementation — this produced
   `unique_artists: 0` / empty `top_artists`/`top_tracks` MVs. Caught immediately by V4;
   fixed by re-copying the current file and re-running the build.
2. **Stale MVs after schema rebuild.** After a `DROP SCHEMA gold CASCADE` (needed twice
   during implementation to pick up new `fact_streams` columns), the 3 MVs stayed
   populated from *before* the drop until `build_star_schema.py` explicitly refreshed
   them — real risk of shipping a stale-but-not-empty view. Fixed by adding an
   unconditional `refresh_all_views()` call at the end of `build_star_schema.py`.

### An investigated, ruled-out non-issue

`/api/reco` and its CSV export showed ~10 of 50 rows with a ±0.0001 score drift against
the baseline (e.g. `0.8027` → `0.8028`). Investigated exhaustively: the DB-backed and
JSON-backed metadata paths were proven to produce **bit-identical** `_track_meta` /
`_artist_meta` dicts (zero diffs across all 808 tracks / 4,079 artists), a bit-identical
feature matrix `X` (`np.array_equal` true), and bit-identical recommendation scores when
both paths are exercised in the same process. The drift traces to the *live API
process* being restarted between the original baseline capture and later verification
runs — a pre-existing, non-Phase-11 characteristic of `StandardScaler`/`cosine_similarity`
under process-to-process floating-point non-associativity, not a Step 8 regression. Two
top-artists/top-tracks CSV "diffs" reported by an early `compare_api_baseline.py` run
were traced to a **bug in the compare script itself** (`Path.read_text()` normalizes
`\r\n`→`\n`, `resp.content` does not) and fixed; a direct byte-level `diff` confirmed
those two files were identical all along.
